# Session summary — 2026-11-02

## Goal
Tidy the planning docs and build roadmap step 1: webcam → landmarks → one
rule-based static gesture ("hand on head") → one key tap.

## What we did
1. **Docs cleanup.** Fixed mismatches between the context files: Python 3.14 and
   uv in SETUP.md, a camera-framing note for "running in place" (knees may be out
   of frame), voice setup filled in, stale open questions removed from STATUS.md.
2. **Checked the stack.** MediaPipe is now 1.2.0 (1.x since Jul 2026). Its Windows
   wheel isn't tied to a Python version and lists 3.9–3.14, so we stayed on 3.14.
   The legacy `mp.solutions` API has been removed; the Tasks API is unchanged. The
   rest of the planned stack (PySide6, Vosk, scikit-learn, PyInstaller, pyarrow,
   pydantic) has Windows 3.14 wheels.
3. **Built step 1** (`src/sww/`, see README.md for the layout):
   - capture thread that keeps only the newest frame
   - PoseLandmarker (lite, VIDEO mode)
   - body frame: origin between the shoulders, y up, unit = shoulder width,
     computed in pixels
   - hand-on-head rule: smooth 0..1 score from four conditions (above nose, not
     overhead, near head centre, elbow bent)
   - state machine: hysteresis (enter 0.6 / exit 0.4) + debounce (50 ms on,
     150 ms off)
   - SendInput with scan codes, dry run by default, `--window` focus gate
   - preview overlay with `--debug` values and `[perf]` stats
   - webcam-free tests (synthetic landmark streams)
4. **First live dry run** worked, but at only 4.9 fps.
5. **Diagnosed with a new `sww bench` command.** The model takes ~11 ms/frame (~89 fps
   ceiling); the camera gave 30 fps with MJPG but 5 fps with uncompressed 720p. The
   driver had ignored our MJPG request. Fixed by sending it before and after the
   frame size. **Result: ~30 fps, noticeably more responsive.**

## Session 2, continued: first real recordings
- Recordings: running + idle, 15 s each, **15 fps** (camera-delivered).
- **Knees are below the image** (y ≈ 1.3, normalised); MediaPipe guessed them, with
  visibility up to 0.74 when standing. No usable knee signal.
- **Arm swing is a strong signal:** wrist peak-to-peak 0.85 running vs 0.06 idle, 1.33 Hz.
  Body bounce also clear (0.23 vs 0.01, 2.6 Hz); not used yet.
- Old arms thresholds flickered (6 starts in 15 s). Swept parameters on both recordings
  and picked swing 0.08–0.18, range 0.15–0.35, recent window 450 ms → one key-down held
  through the whole run, nothing on idle.
- Off-image landmarks are now treated as not visible. Added a 15 fps test and
  replay tests on local recordings. 124 tests pass.

## Session 2, continued: running from the upper body
- Knees removed as an input. Running in place = arm swing AND shoulder bounce
  (min of the two scores); `--forward arms` keeps arm swing alone for seated play.
- Generalised the alternating-knees rule into `oscillation()` over any signal.
- Bounce: shoulders beat hips and nose on the recordings; no median filter (fast signal).
- The new "arms alone must not count as running" test exposed a flaw: per-frame
  scaling by shoulder width turned width jitter into fake bounce. Fixed by scaling
  the window by its median shoulder width. Real-data margins unchanged.
- Real recordings: one key-down for the run, nothing on idle (both modes).
  Synthetic latency at 1.33 Hz: start ~0.5 s, stop ~0.55–0.6 s. 133 tests pass.

## Session 2, continued: labelled recordings
- Two new running recordings with standing before/after. Added `<name>.labels.json`
  ground truth (`sww.labels`), checked by the real-recording tests and printed by
  `sww replay` (start/stop delay per run, `label.running` CSV column).
- One recording flickered W off 0.5 s into a run: body bounce goes *up* from standing
  height, so the "both sides of the baseline" rule failed while the baseline still
  remembered standing. Bounce now scores only the upward side (`sides="up"`);
  synthetic worst case 60/90 flickers -> 0/90, real margins wider.
- Real latency: start 0.8–1.0 s (arm-limited), stop ~0.2 s. 167 tests pass.
